Where this actually stands

The conversation engine is solid and now proven live: on 2026-07-02 all 20 previously-untested scenarios were driven through a real Chatwoot session and passed. 709 tests green, the RAG baseline holds 39/39. The pass surfaced two real bugs (a typed number at a quantity step could be swallowed; the RAG BM25 index column was missing) and three UX nits — all five are fixed, verified live, and locked in with regression tests (commit bc6044d). This is demo-ready and pilot-ready inside the Chatwoot widget today.

It is not production-ready as a WhatsApp service. Three things block that specifically: conversation state lives in an in-memory Python dict that resets on every deploy or crash, there is no WhatsApp Business API connection at all (only the Chatwoot website widget has been exercised), and neither the PRE nor PRO VPS has ever been provisioned — every infra checklist item in TODO.md past DEV is still unchecked.

Layered on top: a handful of commercial rules the bot needs to speak confidently — cancellation deadlines, the Colombian discount, the hotel pickup matrix — are still open questions with the owner after four rounds of Q&A.

Blockers

5 · won't survive a real launch

Nothing here is a code bug — it's scope that was deliberately deferred during dev and now sits directly between this build and a real WhatsApp launch.

No persistent conversation state in-memory dict, src/channels/chatwoot.py

Every conversation lives in a Python dict in process memory. A restart, deploy, or crash silently wipes every in-progress booking. This is the confirmed root cause of the reported "stuck" bugs at MIXED_FINAL_KIDS and MIXED_FINAL_PRIVATE. Migration to Redis/PostgreSQL was deliberately deferred as "the last hardening step before PRE" — that step hasn't been taken yet.

WhatsApp Business API never connected

Chatwoot is only wired to the website widget (chatwoot-test.html, plus the Cloudflare-tunnel public demo). The bot's entire premise is a WhatsApp assistant, and that channel — Meta Cloud API or 360dialog — has not been requested or integrated.

PRE and PRO infrastructure not provisioned TODO.md — infra checklist

docker-compose.vps.yml exists and looks complete, but no VPS has been bought, no DNS configured, and it has never been deployed once. Every item under "PRE (staging)" and "PRO (producción)" in TODO.md is unchecked.

Booking Agent is an empty stub src/agents/booking_agent.py

The whole file is a docstring and one TODO: Implement with Roverd deep link generation. Booking today works entirely through pre-built links in services.json and human escalation — functional, but the "Phase 2" automated booking layer described in the architecture was never started.

Cancellation / payment deadlines still missing from the KB

The bot's behavior is correct and shipped — it states the general policy and always hands off to a human with two buttons. But the actual policy text (how many days before check-in is penalty-free, partial-penalty windows, no-show rule, refund turnaround) was never supplied by the owner across four Q&A rounds. Anyone testing a real cancellation today gets escalation, not an answer.

Important gaps

7 · fix before a wide rollout

Won't stop a controlled pilot, but each one is a live risk of an inconsistent answer, a missed revenue moment, or an operational blind spot once volume goes up.

Colombian discount still undefined questions_for_owner_business_kb.md #2

Confirmed to exist, never closed after 4 rounds. The bot can only say "hay descuento, un asesor te da el detalle" — it cannot quote a number, confirm which services it applies to, or say whether it covers courses.

Pricing source of truth never reconciled questions_for_owner_business_kb.md #1

pricing.json and services.json both hold prices and nobody has decided which one is authoritative when they eventually disagree. No placeholder prices leak today, but the side-by-side review the owner asked for has never happened — this is a silent-drift risk, not a today-bug.

Hotel → pickup matrix mostly unvalidated questions_for_owner_business_kb.md #19

Only San Pedro de Majagua and Cocoliso are confirmed with maritime access. Pao Pao's FAQ was rewritten to express uncertainty rather than overclaim, which is the right interim fix — but the other ~10 priority hotels on the owner's own shortlist (Bora Bora Beach Club, Islabela, Isla del Pirata, Lizamar…) were never validated one by one.

Divemaster stays fully contact-only

No duration, prerequisites, or pricing structure in the KB, so the bot can't pre-qualify a Divemaster lead before escalating — every inquiry, even an obviously non-viable one, reaches a human cold.

Extras / upsells catalog is empty by design

The owner's explicit instruction is "don't offer anything" until the catalog is defined — correctly implemented, but it means a real revenue lever (premium gear, private transport, logbook, extra dives) sits completely idle at launch.

No CI/CD, no DB migrations, no owner dashboard

All three are explicitly unchecked in the TODO.md roadmap: GitHub Actions → VPS pipeline, Alembic migrations for schema changes, and any analytics view of conversations/conversions for the owner. None are launch-blocking on day one, but the longer they're deferred the more manual every release and audit becomes.

Chatwoot isn't operationally ready for the owner's team

No mobile push notifications configured, no conversation tags/labels, and no business-hours auto-message for off-hours contacts. Escalations work technically, but nobody on the human side has been set up to actually notice them reliably yet.

Known code-level issues

5 · small, already located

Concrete, cheap to fix — flagged here so they don't get lost, not because any of them are urgent on their own.

PADI sub-course not set from free text src/agents/supervisor.py:3419

When the IntentDetector routes a free-text message straight to a PADI course, the code sets the generic "course" cart type but the TODO comment confirms the specific course (Open Water vs. Advanced vs. Rescue vs. Divemaster) is never actually written to state — it can silently fall through to a default rather than the one the customer named.

Mixed-group routing decision left open tests/FreeText/test_mixed_group.py

Marked xfail(strict=False), not broken: "Somos dos, yo buceo certificado y mi novia snorkel" currently lands on MIXED_LOCATION (asks origin first) instead of MIXED_ENTRY. The test documents this as a pending design call for Gonzalo, not a regression — worth a deliberate yes/no before launch so it's not accidentally "temporary" forever.

Dead import in the app entrypoint src/main.py:11

conversations is imported from chatwoot.py but never referenced anywhere in main.py. Harmless today, but worth a quick cleanup pass.

Hardcoded Chatwoot token in the public demo route src/main.py — GET /chat

The /chat route embeds a specific website token for the Cloudflare-tunnel testing setup described in docs/PUBLIC_TESTING.md. Correct for that purpose, but it needs to be swapped for the real production inbox token (ideally read from settings, not hardcoded) before this route is ever exposed on a real domain.

Two internal docs are stale docs/kb-audit-mvp.md · docs/mvp-intent-matrix.md

Both predate the Q&A rounds captured in questions_for_owner_business_kb.md — e.g. the KB audit still claims pricing has "many precio_a_definir placeholders," which is no longer true. Not wrong enough to mislead the team today, but worth a pass so a newcomer doesn't read three docs and get three different pictures.

Found & fixed during the pass

5 · all verified live

The live run turned up two real bugs and three UX nits. All are fixed, re-tested in Chatwoot, and covered by regression tests (commit bc6044d, +25 tests).

Fixed Typed number swallowed at quantity steps src/channels/chatwoot.py

Typing a number (e.g. "2" at "¿cuántas personas?") could be dropped as a phantom button-echo because the button's title was the bare number. Real clicks were unaffected. Fixed at the source (don't register ambiguous titles) and unified the webhook + poller echo guards — the poller also lacked the yes/no guard the webhook had.

Fixed RAG running without its BM25 half content_tsv column missing

The full-text column and GIN index were absent on the local DB, so every RAG query silently fell back to vector-only retrieval — the half that helps with proper nouns and exact prices. Applied the FTS migration; all 779 docs indexed. Team gotcha: fresh DB setups must run migrations/001_add_fts_to_kb_documents.sql after a reindex.

Fixed Language mis-detected on Spanish text src/agents/intent_detector.py

Keyword matching was substring-based, so "ahi" matched "hi" and flipped a Spanish message to English. Now whole-word matching. "Estoy en el hotel Pao Pao, me recogen ahi?" now answers in Spanish.

Fixed Payment info question escalated src/agents/escalation.py

The bare verb "pagar"/"pago" escalated info questions like "¿puedo pagar en euros?". Narrowed to real payment-problem phrases; genuine failures ("no puedo pagar", "payment failed") still escalate.

Fixed Advisor offer showed generic menu buttons src/agents/supervisor.py

When a RAG answer offered to connect the user with an advisor (contact-only courses like Divemaster), it showed "Reservar / Información" instead of advisor buttons. Now detected (robust to the LLM's varying wording) and given matching advisor/home buttons.
